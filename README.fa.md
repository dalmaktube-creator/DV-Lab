# DV Lab — 0.2.0-preview.7

مادر MCP و عامل سبک برای اجرای مستقل آزمایش‌های شبکه روی چند سرور. **نسخه پیش‌نمایش است، نه محصول تأییدشده برای سرور پروداکشن.**

## چه چیزی ساخته شده؟

- یک مادر HTTPS با MCP Streamable HTTP و صف کار SQLite؛ وابستگی Python بیرونی ندارد.
- عامل روی هر سرور فقط اتصال خروجی HTTPS به مادر می‌سازد؛ کلید SSH سرورها به مادر داده نمی‌شود.
- ارتباط مستقیم TCP/UDP میان IP عمومی سرورهای عضو، فقط در محدوده پورت آزمایش. این نسخه شبکه مش یا تونل ترانزیتی عمومی نیست.
- ترمینال آزاد داخل یک کپسول rootless Podman؛ اجرای همزمان حداکثر ۴ کار، مهلت هر کار ۱ تا ۳۰۰ ثانیه، لاگ حلقوی ۶۴KiB.
- فایل، لاگ، وضعیت پردازش، لغو کار، توقف/ادامه نود و نمونه‌های CPU/RAM از راه MCP.
- منوی ANSI رنگی `sudo dv-lab`، لینک bootstrap بدون رمز و کد عضویت یک‌بارمصرف با اعتبار ۱۰ دقیقه.
- حداکثر ۱۶ نود. احراز هویت مادر، مدیر و هر عامل مستقل است.

## معماری و مرز آزادی

```text
Notion / MCP client ── HTTPS + bearer ── Mother
                                          ▲
                         outbound HTTPS   │
                            ┌─────────────┴─────────────┐
                       Iran agent                 Turkey agent
                            │                           │
                      rootless capsule ← TCP/UDP → rootless capsule
                      private /work                 private /work
```

MCP هیچ ابزار shell روی میزبان، تغییر فایروال عمومی، نصب بسته روی میزبان یا خواندن `/root` ندارد. داخل کپسول می‌توان کد اجرا کرد، TUN ساخت، ابزارهای منتقل‌شده را اجرا کرد و روی پورت‌های مجاز تست واقعی گرفت. نصب بسته دلخواه با apt داخل کپسول ممکن نیست: ریشه فقط‌خواندنی است؛ ابزارهای پایه از قبل در تصویر هستند. فایل اجرایی اضافه را به `/work` انتقال دهید. اینترنت عمومی از کپسول بسته است؛ فقط مادر، DNS تنظیم‌شده و همتایان/پورت‌های آزمایش مجازند.

کپسول ماشین مجازی نیست؛ کرنل، CPU، دیسک و کارت شبکه با میزبان مشترک‌اند. خطر آسیب صفر تضمین نمی‌شود. برای آزمایش‌های سنگین، سرور اختصاصی آزمایش توصیه می‌شود. جزئیات در SECURITY.md.

## پیش‌نیاز نسخه اول

- مادر: Ubuntu 22.04 یا 24.04؛ عامل ایزوله: Ubuntu 22.04 یا 24.04. هر دو به systemd و cgroup v2 نیاز دارند. IPv4 عمومی قابل دسترسی روی هر نود؛ NAT مشترک/IPv6 در این نسخه پشتیبانی نشده است.
- دسترسی root فقط برای نصب یک‌باره و تأیید حدود منابع. درخواست root از طریق MCP وجود ندارد.
- مادر: دامنه و گواهی معتبر HTTPS با fullchain و کلید موجود روی همان سرور؛ پورت مستقیم آزاد >=1024، مثلاً 8443.
- عامل: `/dev/net/tun` قابل استفاده توسط حساب غیرریشه، حداقل 1GiB فضای آزاد نصب، پورت‌های آزاد 45100–45107 TCP و UDP.
- نصب اولیه برای apt و ساخت تصویر به اینترنت احتیاج دارد. دانلود/ساخت تصویر هزینه نصب است، نه مصرف پایدار زمان تست.
- نصب‌کننده nginx، SSH، Docker، تونل قبلی یا قوانین فایروال موجود را بازنویسی/حذف نمی‌کند. ممکن است لازم باشد اپراتور در فایروال موجود فقط دسترسی بین همتایان به پورت‌های آزمایش را مجاز کند. قواعد خود ابزار هیچ deny موجود را خنثی نمی‌کنند.

## نصب مستقیم از GitHub و آپدیت

بعد از عمومی‌شدن ریپو و سبزشدن همهٔ آزمون‌های لازم CI:

```bash
curl -fsSL https://raw.githubusercontent.com/dalmaktube-creator/DV-Lab/main/install.sh | sudo bash
```

نصاب نقش مادر/عامل را می‌پرسد. سورس به کامیت دقیق main قفل می‌شود و هویت فایل‌ها با Git tree همان کامیت بررسی می‌شود. روی ریپوی Private، این فرمان بدون احراز هویت کار نمی‌کند؛ توکن GitHub هم در نصاب جمع‌آوری نمی‌شود.

برای آپدیت: گزینه‌های U/S/R در منوی `sudo dv-lab` یا:

```bash
sudo dv-lab update check
sudo dv-lab update status
sudo dv-lab update apply FULL_COMMIT_SHA
sudo dv-lab update rollback
```

من هم بعد از انتشار تغییر با موری یا GitHub MCP می‌توانم با `lab_update` یک نود را مرحله‌ای آپدیت کنم؛ مادر آخر آپدیت می‌شود. لازم نیست دوباره وارد SSH شوی. آپدیت کارهای آزمایش را متوقف می‌کند و `/work` پاک می‌شود، پس فایل‌ها اول باید برداشته شوند. در صورت قطع پاسخ، وضعیت نسخه را بررسی می‌کنیم، نه اجرای کورکورانه مجدد.

مرز اعتماد: کامیت‌های main همین ریپو با تأیید CI. این به معنی امضای مستقل یا بی‌خطر بودن هر کد نیست. عامل فقط کد برنامهٔ غیرریشه را آپدیت می‌کند؛ نگهبان root، launcher ثابت کنسول، فایروال، سرویس، بسته‌های میزبان، تصویر پایه و سقف منابع خودکار تغییر نمی‌کنند. آزمون سلامت و بازگشت وجود دارد، اما خرابی دیسک/کرنل یا قطع برق تضمین بازیابی مطلق ندارد. [شرح کامل آپدیت](UPDATE.md).

یک استثنای عمدی در mount وجود دارد: فقط پوشهٔ کوچک، عمومی و فقط‌خواندنی کد کپسول از میزبان متصل می‌شود تا runner همراه برنامه آپدیت شود؛ هیچ تنظیمات/توکن/مسیر دادهٔ میزبان در آن نیست.

## نصب مادر

فایل ZIP را روی مادر منتقل و استخراج کنید؛ داخل پوشه `dv-lab`:

```bash
sudo bash install.sh hub
sudo dv-lab
```

نصب‌کننده ابتدا دامنهٔ خالی مثل `lab.example.com` و سپس پورت را می‌پرسد؛ آدرس HTTPS را خودش می‌سازد. دیگر مسیر PEM لازم نیست. قبل از تغییر سیستم، خلاصه و تأیید INSTALL نمایش داده می‌شود. این تأیید، پذیرش شرایط Let’s Encrypt را هم شامل می‌شود؛ حساب ACME بدون ایمیل ساخته می‌شود.

### گواهی و تمدید خودکار

- گواهی‌های Certbot در `/etc/letsencrypt/live` و فضای اختصاصی DV Lab شناسایی می‌شوند. زنجیره اعتماد، تطابق دامنه و کلید و تاریخ اعتبار بررسی می‌شود؛ تنظیم تمدید باید خودکار و بدون hook توقف سرویس یا installer وب‌سرور باشد.
- گواهی مناسب با تست staging تمدید بررسی و بدون صدور تکراری استفاده می‌شود. تمدید واقعی فقط در صورت موعد مقرر Certbot انجام می‌شود، نه با force. شکست تست تمدید باعث درخواست کورکورانه گواهی تکراری نمی‌شود.
- در نبود گواهی قابل‌مدیریت، ابتدا HTTP-01 روی staging تست و سپس گواهی واقعی در `/etc/dv-lab/acme` صادر می‌شود. **DNS باید به همین سرور اشاره کند و TCP 80 از اینترنت قابل‌دسترسی و روی سرور آزاد باشد؛ این شرط مستقل از پورت MCP مثل 2086 است.** پروکسی DNS خاموش باشد. گواهی‌های ابزارهای دیگر یا تنظیمات ناسازگار به‌زور تغییر داده نمی‌شوند.
- هیچ nginx، Apache یا سرویس دیگری برای صدور متوقف نمی‌شود؛ فایروال هم خودکار تغییر نمی‌کند. اگر پورت 80 اشغال باشد، صدور standalone متوقف می‌شود؛ صدور DNS خودکار جدید با اعتبارنامه ارائه‌دهنده در این نسخه پیاده نشده است. lineage موجود webroot یا DNS می‌تواند با تنظیم سالم خودش استفاده شود.
- تایمر `dv-lab-tls-renew.timer` روزی دو بار با تأخیر تصادفی، فقط همان lineage را بررسی می‌کند؛ daemon بیکار جدید ندارد. helper تمدید root-owned و در نصب اولیه ثابت است و از مسیر قابل‌آپدیت برنامه اجرا نمی‌شود.
- جفت گواهی در نسل‌های مجزا با کلید 640 و گروه dvlab-hub کپی می‌شود؛ سوییچ اتمیک `tls/current` جلوی جفت نصفه را می‌گیرد. پس از تغییر واقعی گواهی، فقط مادر restart و HTTPS محلی با SNI دامنه بررسی می‌شود؛ در شکست، جفت قبلی بازگردانده می‌شود. دو نسل نگه داشته می‌شود.
- فعال‌بودن تایمر و موفقیت تست فعلی، تضمین آینده نیست: DNS، دسترسی challenge و اعتبارنامه احتمالی DNS باید سالم بمانند. وضعیت: `systemctl status dv-lab-tls-renew.timer` و خطاها: `journalctl -u dv-lab-tls-renew.service`.

کلید خصوصی را در چت ارسال نکنید. گواهی یا فایل کلید داخل بسته bootstrap قرار نمی‌گیرد. تست‌ها با CA محلی مورداعتماد و درخواست ACME شبیه‌سازی‌شده اجرا می‌شوند؛ تا صدور روی دامنه واقعی شما، ادعای صدور زنده برای آن نداریم.

## اضافه‌کردن ایران، ترکیه یا سرورهای بعدی

در منوی مادر گزینه ۲ را بزنید. منو این‌ها را می‌دهد:

1. فرمان دانلود bootstrap بدون توکن در URL؛ فایل را می‌توانید قبل از اجرا بررسی کنید.
2. کد عضویت یک‌بارمصرف؛ آن را فقط در پرسش مخفی نصب‌کننده نود وارد کنید.

فرمان bootstrap را یک‌بار روی سرور مقصد اجرا کنید. نصب‌کننده نام نود و کد را می‌پرسد و پس از تأیید، حساب اختصاصی، تصویر، سرویس و جدول فایروال خود را ایجاد می‌کند. قطع‌شدن نصب ممکن است عضویت مصرف‌شده و بخشی از نصب را باقی بگذارد؛ نصب‌کننده عمداً reinstall مخرب ندارد. در این حالت دوباره کورکورانه اجرا نکنید؛ وضعیت محلی را بررسی کنید.

مادر هم می‌تواند نود باشد؛ نقش عامل را جداگانه روی همان میزبان نصب کنید. حساب و بودجه مادر و عامل از هم جدا می‌مانند. لینک bootstrap زنده بعد از نصب مادر در دسترس است.

## اتصال MCP

گزینه ۳ منوی مادر، آدرس زیر و توکن مخصوص MCP را محلی نمایش می‌دهد:

```text
https://YOUR-MOTHER:8443/mcp
Authorization: Bearer <MCP token>
Transport: Streamable HTTP
```

توکن را در ورودی امن اتصال MCP وارد کنید، نه در چت و نه داخل URL. سازگاری نهایی باید با کشف ابزارها از کلاینت واقعی تأیید شود. این بسته هنوز به حساب Notion شما متصل نشده است. از انتشار عمومی توکن/پورت بدون احراز هویت خودداری کنید.

## ابزارهای MCP

| ابزار | کاربرد |
|---|---|
| lab_nodes | نودها، IP، پورت‌ها، بودجه و heartbeat |
| lab_resources | خواندن/تغییر CPU و RAM آزمایش در سقف اولیه، با revision و نتیجهٔ غیرهمزمان |
| lab_exec | shell فقط داخل کپسول؛ صف غیرهمزمان |
| lab_action | دریافت نتیجه کار صف‌شده |
| lab_logs | خواندن خروجی پردازش با cursor |
| lab_kill | توقف پردازش/گروه فرزند معمول آن |
| lab_list | حداکثر ۲۰۰ نام فایل داخل `/work` |
| lab_write | نوشتن اتمیک حداکثر ۶۴KiB base64 |
| lab_read | خواندن بازه حداکثر ۶۴KiB فایل معمول |
| lab_metrics | شمارنده و تاریخچه CPU/RAM کپسول و کل حساب آزمایش |
| lab_pause | درخواست توقف و حذف کپسول نود |
| lab_resume | اجازه ساخت مجدد با همان محدودیت‌ها |
| lab_update | بررسی، وضعیت، اعمال کامیت مشخص یا بازگشت برنامه روی مادر/نود |

کارهای نود یک `action` می‌دهند؛ با `lab_action` تا نتیجه نهایی پیگیری کنید. `lab_exec` پس از اجرا شناسه `process` می‌دهد؛ خروجی/توقف با آن انجام می‌شود. نتیجه گم‌شده خودکار دوباره اجرا نمی‌شود، چون ممکن است دستور قبلاً اجرا شده باشد.

برای فایل بزرگ، قطعات ۶۴KiB را در فایل‌های جدا بنویسید، داخل کپسول با ترتیب درست `cat` کنید و SHA256 فایل نهایی را بررسی کنید. خواندن نیز offset دارد. عامل می‌تواند با ترکیب این ابزارها فایل را بین نودها منتقل کند؛ در این نسخه ابزار انتقال مستقیم سروربه‌سرور مستقل وجود ندارد. `/work` موقتی است: با pause، توقف کپسول یا راه‌اندازی مجدد حذف می‌شود. خروجی لازم را قبل از توقف بردارید.

## اندازه‌گیری CPU بدون ابهام

هر ثانیه، نمونه سبک و بدون اجرای subprocess از شمارنده‌های cgroup گرفته می‌شود؛ آخرین ۱۸۰ نمونه در حافظه نگهداری می‌شود. سربار آن باید روی سرور واقعی سنجیده شود؛ عدد مصرف بیکار هنوز اندازه‌گیری نشده است.

- `result.samples`: کپسول، شامل خود اندازه‌گیر داخل کپسول.
- `lab_account.samples`: کل حساب آزمایش، شامل عامل، Podman/conmon، شبکه user-mode و کپسول؛ نمونه‌ها `cpu_percent_one_core` و `cpu_percent_host_capacity` دارند.
- دو مجموعه را **با هم جمع نکنید**: کپسول زیرمجموعه حساب آزمایش است.
- ۵۰٪ یک هسته روی ماشین دو هسته‌ای = ۲۵٪ ظرفیت کل، نه ۵۰٪ کل سرور.
- `nr_throttled` و `throttled_usec` مشخص می‌کنند سقف CPU در تست دخالت داشته یا نه.
- برای مقایسه تونل‌ها، زمان، نرخ، جهت، پروتکل و شمار جریان‌ها باید یکسان باشند. CPU سازنده بار هم در حساب آزمایش دیده می‌شود؛ CPU خالص تونل نیست.
- مصرف کل میزبان/سرویس‌های تولیدی خوانده نمی‌شود؛ این مرز عمدی است. جلوگیری قطعی از افت سرویس‌های دیگر یا توقف بر اساس CPU کل میزبان ادعا نمی‌شود.

## حدود پیش‌فرض؛ نه مصرف تضمین‌شده

| بخش | سقف CPU | سقف RAM | توضیح |
|---|---|---|---|
| حساب عامل + شبکه + کپسول | 0.5 هسته | 192MiB | PID حداکثر ۱۲۸، swap صفر |
| خود کپسول | 0.4 هسته | 128MiB | PID حداکثر ۶۴، swap اضافه صفر |
| مادر مستقل | 0.25 هسته | 256MiB | سقف سرویس، نه مصرف معمول |

کپسول فقط با اولین عملیات ساخته می‌شود؛ در بیکاری بیش از ۱۰ دقیقه متوقف می‌شود. ۶۰ ثانیه قطع کنترل، watchdog محلی درخواست حذف آن را می‌دهد. این زمان‌بندی تضمین real-time تحت OOM/اشکال کرنل نیست. توقف سرویس نیز cleanup دارد.

این سقف‌های محافظه‌کارانه می‌توانند سقف مگابیت را پایین بیاورند؛ تا وقتی throttling وجود دارد نتیجه «حداکثر توان تونل» نیست. بودجه با ابزار `lab_resources` در سقف ثابتِ تأییدشده هنگام نصب قابل تغییر است؛ تغییر سقف مطلق root جزو آپدیت معمول برنامه نیست. شبکه rootless نیز سربار CPU دارد؛ مقایسه با Easy Mesh روی میزبان بدون کنترل این سربار منصفانه نیست.

## توقف و عیب‌یابی

```bash
sudo dv-lab
# توقف اضطراری محلی نود؛ فقط آزمایش، نه سرویس‌های تولیدی:
sudo dv-lab --emergency-stop
# وضعیت مادر:
sudo systemctl status dv-lab-hub --no-pager
sudo journalctl -u dv-lab-hub -n 50 --no-pager
```

توقف از مادر غیرهمزمان است؛ برای وضعیت قطعی heartbeat را بررسی کنید. توقف محلی از منو سرویس عامل را هم متوقف می‌کند. پس از رفع مشکل، گزینه restart نود قابل استفاده است. فایل root-owned شبکه با DNS/IPهای زمان نصب ساخته می‌شود؛ تغییر IP مادر یا DNS مستلزم بررسی اپراتور و به‌روزرسانی همین تنظیمات است، نه بازکردن عمومی فایروال.

## آزمون و سطح اطمینان

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q dvlab
bash -n install.sh
```

۹۵ آزمون محلی پاس شده‌اند: احراز هویت تفکیک‌شده، کد یک‌بارمصرف، صف/lease بدون اجرای مجدد، pause/offline، framing HTTP/notification، TLS واقعی روی localhost و رد گواهی نامعتبر، فایل/لینک/FIFO، مهلت/لغو/حد لاگ، argv محدود Podman، محاسبه CPU و بسته‌بندی.

**انجام‌نشده روی سرورهای شما:** نصب end-to-end روی Ubuntu، ایجاد واقعی rootless Podman/TUN، اعمال واقعی nft/cgroup و reboot، کشف ابزار در اتصال Notion و سنجش throughput/مصرف بیکار روی ایران و ترکیه. محیط ساخت محلی Podman/systemd عملیاتی ندارد؛ CI اوبونتو برای smoke واقعی rootless/TUN/cgroup/nft تعریف شده، اما تا نتیجه واقعی آن دیده نشود نباید پاس‌شده فرض شود. عبور unit test به معنی عبور نصب کامل یا تست چندسروری نیست. فایل CHECKLIST.md در ZIP روند پذیرش یک‌باره است؛ این بررسی‌ها برای توسعه‌دهنده/اپراتورند، نه درخواست تکرار بنچمارک دستی از شما.

### Ubuntu 22.04

مادر و نود هر دو روی Ubuntu 22.04 و 24.04 پشتیبانی می‌شوند. تست‌های واقعی ایزوله‌سازی روی هر دو نسخه و نصب مادر روی هر دو تعریف شده‌اند؛ نتیجهٔ هر انتشار را در Actions ببینید. برای Jammy، فقط به مدیر کاربر اختصاصی آزمایش، کنترلرهای cpu/memory/pids واگذار می‌شوند؛ AppArmor یا sysctl عمومی ضعیف نمی‌شود. Podman قدیمی با آرگومان سازگار پاک‌سازی می‌شود. میزبان همچنان باید کرنل/مجوز user namespace، cgroup v2 و TUN مناسب داشته باشد؛ ردکردن چنین میزبان نامناسبی نقصی نیست که با دورزدن ایزوله‌سازی حل شود.

### رابط نصب

مرحله‌های شماره‌دار و رنگی، نمونهٔ کوتاه ورودی، مرور تنظیمات قبل از تأیید و امکان اصلاح آدرس/پورت/فایل PEM بدون traceback. خروجی طولانی فرمان‌ها در لاگ خصوصی root ذخیره می‌شود و در خطا مسیرش نمایش داده می‌شود. هیچ سرویس اشغال‌کنندهٔ پورت خودکار متوقف نمی‌شود. رنگ با NO_COLOR یا خروجی غیرترمینالی خاموش می‌شود. شمارهٔ مرحله نشان‌دهندهٔ کار واقعی است، نه درصد ساختگی پیشرفت.

### مدیریت منابع و آپدیت بدون SSH تکراری

بعد از نصب اولیه نود، مدل می‌تواند `lab_resources` را با action=status فراخوانی کند و حدود فعلی، سقف اولیه و revision را بگیرد. برای set هر چهار مقدار `account_cpus`، `account_memory_mib`، `capsule_cpus` و `capsule_memory_mib` و همان revision لازم است؛ نتیجه از `lab_action` گرفته می‌شود. تغییر منابع کارهای کپسول و `/work` موقت را حذف می‌کند؛ ابتدا فایل‌های لازم را خارج کنید.

نصاب سقف مطلق را پیش از تأیید نشان می‌دهد: حداکثر ۷۵٪ شمار CPU منطقی تا سقف ۴ هسته، و ۲۵٪ RAM میزبان تا سقف ۲۰۴۸MiB؛ کف سقف‌ها ۰٫۵ CPU و ۱۹۲MiB است. بودجه آغازین همان ۰٫۵/۱۹۲ برای حساب و ۰٫۴/۱۲۸ برای کپسول می‌ماند؛ این سقف‌ها مصرف بیکار نیستند. حداقل ۰٫۱ CPU و ۶۴MiB برای بخش بیرون کپسول نگه داشته می‌شود. کاهش حافظه علاوه بر مصرف واقعی، ۳۲MiB حاشیه می‌خواهد؛ PID و swap تغییر نمی‌کنند.

کنترل منابع توسط helper ثابت root با احراز UID واقعی و socket محلی انجام می‌شود؛ فقط slice حساب آزمایش، config عامل و drop-in ثابت مجازند. تنظیم واقعی cgroup بررسی، برای reboot ذخیره و در خطای عادی بازگردانده می‌شود. helper فقط هنگام درخواست اجرا می‌شود (سقف ۱۰٪ CPU و ۶۴MiB)؛ daemon بیکار اضافه ندارد. سقف مطلق یا helper root از مسیر آپدیت برنامه عوض نمی‌شود.

آپدیت برنامهٔ مادر موجود با `lab_update` از همین MCP انجام می‌شود و منوی دستی هم باقی است. برای نودهای تازه، کنترل منابع در همان نصب اولیه قرار دارد و نیازی به نصب دستی مرحلهٔ دوم نیست. نودهای قدیمی فاقد این helper یا تغییرات سیاست root به مهاجرتِ بررسی‌شده نیاز دارند؛ دسترسی ریشهٔ نامحدود برای حذف کار دستی ایجاد نشده است.

### منوی خوانا و اتصال امن نود

خروجی هر گزینه تا زدن Enter باقی می‌ماند؛ منو بلافاصله روی نتیجه چاپ نمی‌شود. URL بوتسترپ و کد یک‌بارمصرف کارت رنگی جدا دارند. خود URL یک خط بدون پیشوند/پسوند تزئینی است تا کپی خراب نشود؛ فرمان نصب نود هم جدا نمایش داده می‌شود و هیچ کدی در URL نیست.

نود دامنه، گواهی جدا یا وب‌سرور مدیریتی ورودی لازم ندارد: خودش با HTTPS به مادر وصل و گواهی مادر را اعتبارسنجی می‌کند؛ پس از عضویت، توکن اختصاصی دارد. این امنیت کانال کنترل است، نه ادعای رمزنگاری خودکارِ هر ترافیک تست بین نودها؛ برای تست دادهٔ مصنوعی استفاده کنید و رمزنگاری تونل موردآزمایش را جدا بسنجید.

در نصب جدید، launcher کوچک root اول سطح دسترسی را به حساب اختصاصی پایین می‌آورد و بعد UI قابل‌آپدیت را اجرا می‌کند؛ UI متغیر هیچ‌وقت با root لود نمی‌شود. مادرهای قدیمی با منوی root ثابت، فقط یک‌بار **بعد از آپدیت برنامه به همین کامیت** نیاز دارند:

```bash
curl -fsSL https://raw.githubusercontent.com/dalmaktube-creator/DV-Lab/main/install.sh | sudo bash -s -- console-upgrade
```

این نصب مجدد نیست؛ فقط launcher را با نسخهٔ قبلیِ پشتیبان‌شده به حالت کم‌اختیار منتقل می‌کند. تطابق کامیت نصب‌شده/دانلودشده الزامی است. سرویس، توکن، TLS، فایروال و بودجه‌ها تغییر نمی‌کنند. بعد از آن اصلاحات UI هم با آپدیت عادی مدل اعمال می‌شوند؛ سیاست‌های root همچنان خودکار بازنویسی نمی‌شوند.

دو job نصب کامل نود، خود نصاب واقعی، مادر HTTPS در namespace جدا، عضویت/heartbeat خروجی، اجرای کپسول از MCP و تغییر واقعی منابع را روی ۲۲ و ۲۴ بررسی می‌کنند. در این تست فقط پاسخ‌های ترمینال از قبل داده می‌شوند؛ شبکه و Podman/cgroup شبیه‌سازی نمی‌شوند. آدرس‌های ویژهٔ آزمایشی فقط داخل ماشین موقت route می‌شوند.
